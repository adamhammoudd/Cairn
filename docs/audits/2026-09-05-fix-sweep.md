## 1. Currency setting isn't actually applied everywhere - FIXED (Ticker, Alerts' active list,
   Billing, and 4 more spots the sweep found)

**Root cause, Ticker page:** `ticker-workspace.tsx`'s local formatter -

```ts
const usd = (n: number | null) => (n === null ? "-" : n.toLocaleString(undefined, { style: "currency", currency: "USD" }));
const money = isForex ? rate : isIndex ? level : usd;
```

- hardcoded `currency: "USD"` instead of routing through `formatMoney(n, prefs)` (the helper
Markets/Portfolio/Comparison already use). Same pattern, same file: the avg-cost subline
(`avgCost.toLocaleString(..., currency: "USD")`) and `technicals-panel.tsx`'s SMA/EMA chart
axis/tooltip formatter.

**Root cause, Alerts:** `lib/alerts.ts`'s `describeCondition()` (the active-alert-list condition
text, e.g. "Price above $221") - `` `Price ${condition.comparator} $${condition.value}` ``,
same hardcoded `$`. The specific example the review quoted ("NVDA is above $221 (last close
$227.98)") is a **different, frozen** string - see below.

**Root cause, Billing:** `billing-settings-panel.tsx` - literal `"$0"` for the free plan.

**The sweep also found (not named in the review), all fixed the same way:** `formatMarketCap()`
(`lib/screener.ts`) hardcoded `$` - used by Markets, Screener, Comparison's aligned-metrics table,
and Ticker's own market-cap stat, so this one function fix covers five surfaces at once.

**Fixed:**
- `ticker-workspace.tsx`: `money`/`currency` now calls `formatMoney(n, prefs)`; avg-cost subline
  same.
- `technicals-panel.tsx`: chart axis/tooltip formatter now calls `formatMoney(n, prefs)`.
- `formatMarketCap(n, prefs)` (was `formatMarketCap(n)`) - converts via `prefs.fxRate`, compact
  Intl currency notation. All 6 call sites (`comparison-table.tsx`, `ticker-list.tsx`,
  `screener-panel.tsx`, `ticker-workspace.tsx` ×2) updated to pass `prefs`.
- `describeCondition(type, condition, prefs?)` - the active alert list now shows "Price above
  €203" on a EUR account; `prefs` is optional so the signature stays callable with no request
  scope (no live caller currently needs that, matches every other pure formatter's convention).
- New `currencySymbol(prefs)` in `lib/display-prefs.ts` - just the symbol, for a label context
  (not a full formatted amount).
- `billing-settings-panel.tsx`: `"$0"` → `formatMoney(0, prefs)`.

**Not fixed, explained (see E5):** `lib/ai/portfolio-summary.ts`'s `money()`. **Not fixed, a
frozen historical string** (same category as last week's chat-citation E3): the exact delivery
message the review quoted is composed once, server-side, at evaluation time, by
`lib/alerts.ts`/`evaluate-alerts` (Deno mirror) with no per-user display prefs in scope inside a
batch cron job - threading FX conversion through a scheduled system-wide evaluator (in both the
Node and Deno copies) is a materially bigger change than "route through the existing helper," and
I have no way to verify it end-to-end without either mutating real delivery rows or trusting an
unverified prompt-adjacent change. The **active alert condition list** (which most of the time is
what a user is actually looking at) is fixed; the historical delivery log's frozen text isn't.

**Test:** `npm run test:currency-formatting` (13/13) - checks `currencySymbol`, `formatMarketCap`,
and `describeCondition` all agree on the same symbol for the same `DisplayPrefs`, re-run under
both EUR and USD (not just "does €/$ show up somewhere," which the old always-USD code would
still coincidentally pass under a USD account).

## 6. BTC portfolio value doesn't fully reconcile with its price - root cause was display
   precision, not data; fixed

Did the arithmetic with real, live-checked numbers: BTC holding quantity `0.000544`, live price
(Twelve Data, checked 2026-09-05) `$79,724.77`. True value: `$43.37`. The Holdings table printed
quantity capped at `maximumFractionDigits: 4`, i.e. **"0.0005"** - manually multiplying that
*displayed* quantity by the *displayed* price gives `$39.86`, an **8.09% gap** from the row's own
(correctly computed, full-precision) value - matching the review's "roughly 8%" exactly.
`computeHoldingMetrics` was never wrong (`value = currentPrice * h.quantity` always uses the full,
untruncated number); only what got *printed* in the Quantity column was lossy enough to make a
reader's own check disagree with the app's own math.

**Fixed:** new `formatQuantity()` (`lib/portfolio.ts`) - up to 8 decimal places for a holding under
1 unit (crypto-sized fractions), the existing 4 for anything ≥ 1 (share counts). Wired into
`holdings-table.tsx`'s one quantity cell (the only place that rendered it).

**Test:** `npm run test:btc-value-reconciliation` (7/7) - reproduces the exact 8.09% gap under the
old rounding using the real live numbers above, confirms the new formatter closes it to <0.01%,
and confirms whole-share quantities (10, 2.5) are unaffected.
